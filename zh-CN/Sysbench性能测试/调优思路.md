本文将介绍Sysbench性能测试的调优思路，包括数据库层面的调优和数据库运行环境的调优。

## 调优操作

### 操作系统调优

在NUMA架构中，进行Sysbench性能测试时，操作系统层面的调优对于充分发挥数据库性能至关重要。

#### 关闭透明大页

透明大页可能会导致内存分配延迟，建议关闭透明大页：

```bash
# 临时关闭透明大页（重启后失效）
$ echo never > /sys/kernel/mm/transparent_hugepage/enabled
$ echo never > /sys/kernel/mm/transparent_hugepage/defrag

# 永久关闭透明大页，需修改grub配置

# CentOS/RHEL
$ vi /etc/default/grub
# 在GRUB_CMDLINE_LINUX中添加：transparent_hugepage=never

# KylinOS V10
# 查看当前grub配置
$ cat /boot/efi/EFI/*/grubenv
# 编辑grub配置
$ vi /etc/default/grub
# 在GRUB_CMDLINE_LINUX中添加：transparent_hugepage=never
# 重新生成grub配置
$ grub2-mkconfig -o /boot/efi/EFI/*/grub.cfg
```

#### 调整CPU调度策略

对于数据库这种延迟敏感型应用，建议使用performance调度策略：

```bash
# 设置CPU调度策略为performance
$ cpupower frequency-set -g performance

# 查看当前CPU调度策略
$ cpupower frequency-info
```

#### 网络配置调优

与TPC-C测试类似，当客户端和服务端部署在不同服务器上时，网络传输将成为性能瓶颈。可以通过优化网卡中断队列来提升网络性能。

```bash
# 查看网卡设备名
$ ifconfig

# 查看网卡中断队列信息
$ ethtool -l enp1s0f0np0

# 设置网卡中断队列数
$ ethtool -L enp1s0f0np0 combined 32
```

### 数据库调优

#### 数据库进程绑核

在多NUMA节点环境中，将数据库进程绑定到特定的NUMA节点可以提高缓存命中率：

```bash
# 将数据库进程绑定到NUMA node 1,2,3
$ numactl --cpunodebind=1,2,3 --membind=1,2,3 yasdb open
```

#### 数据库文件分盘存储

合理规划数据文件的存储位置，将redo文件和数据文件分盘部署：

```sql
-- 创建数据库时将redo文件和数据文件分盘存储
CREATE DATABASE yashandb
LOGFILE(
    '/data1/redo1' size 50G BLOCKSIZE 512,
    '/data2/redo2' size 50G BLOCKSIZE 512,
    '/data3/redo3' size 50G BLOCKSIZE 512,
    '/data4/redo4' size 50G BLOCKSIZE 512,
    '/data5/redo5' size 50G BLOCKSIZE 512,
    '/data6/redo6' size 50G BLOCKSIZE 512,
    '/data7/redo7' size 50G BLOCKSIZE 512,
    '/data8/redo8' size 50G BLOCKSIZE 512,
    '/data9/redo9' size 50G BLOCKSIZE 512,
    '/data10/redo10 size 50G BLOCKSIZE 512)
UNDO TABLESPACE DATAFILE '/data2/undo' size 40G
DEFAULT TABLESPACE DATAFILE '/data2/users' size 500G;
```

| 配置项 | 推荐值 |
| --- | --- |
| redo分盘部署 | 大小50G * 10，BLOCKSIZE 512 |
| undo大小 | 增大到40G |
| tablespace | 根据实际数据量创建，需提前创建 |

#### 数据库核心参数调优

以下列举了Sysbench测试推荐的数据库核心配置参数：

| 参数 | 说明 | 推荐值 |
| --- | --- | --- |
| DATA_BUFFER_SIZE | 影响数据库缓存buffer的大小 | 根据内存情况配置 |
| MAX_SESSIONS | 影响实际并发数量 | 根据并发需求配置 |
| MAX_REACTOR_CHANNELS | 大并发下，推荐开启共享模式 | 较大值 |
| MAX_WORKERS | 工作线程数 | CPU*(2-3)，取决于实际的测试效果 |
| SHARE_POOL_SIZE | 共享池大小，大并发下需要设置更大 | 2000并发建议10G |
| OPEN_CURSORS | 大并发下需考虑增加 | 较大值 |
| UNDO_RETENTION | Undo保留时间 | 根据需求配置 |
| UNDO_SHRINK_ENABLED | 是否启用Undo自动收缩 | FALSE |
| _CONSISTENT_WRITE | 语句级一致性写入，避免索引不一致 | TRUE |

#### 性能优化参数

如需追求更高性能，可考虑设置以下参数：

| 参数 | 说明 | 推荐值 |
| --- | --- | --- |
| DOUBLE_WRITE_ENABLED | 是否启用双写 | FALSE |
| COMMIT_WAIT | 提交等待策略 | NOWAIT |

> **Caution**:
>
> 关闭双写（DOUBLE_WRITE_ENABLED=FALSE）可以提升性能，但会增加数据丢失风险，建议仅在测试环境使用。

#### 数据库参数调优

以下列举了Sysbench测试推荐的数据库配置参数：

```bash
# 数据缓冲区大小，建议配置为规划内存的80%
DATA_BUFFER_SIZE=180G

# 数据缓冲区分区数，大并发场景下可降低缓存区锁冲突
_DATA_BUFFER_PARTS=8

# 虚拟机缓冲区大小
VM_BUFFER_SIZE=30G

# 虚拟机缓冲区分区数
VM_BUFFER_PARTS=8

# Undo保留时间
UNDO_RETENTION=30

# 关闭undo自动收缩
UNDO_SHRINK_ENABLED=FALSE

# 检查点超时时间
CHECKPOINT_TIMEOUT=1000000000

# 共享池大小
SHARE_POOL_SIZE=2G

# 会话预留游标数
_SESSION_RESERVED_CURSORS=64

# 大页内存
USE_LARGE_PAGES=ONLY
LARGE_POOL_SIZE=4G

# Redo日志直接写入模式
REDOFILE_IO_MODE=DIRECT
```

### Sysbench测试参数调优

#### 并发线程数调优

并发线程数是影响Sysbench测试结果的关键因素。通常建议从较低的并发数开启测试，随后逐步提升，以此探寻最佳性能点。推荐按照`--threads=32 → 64 → 128 → 256 → 512 → 1024`阶梯式递增方式进行，并密切留意TPS的拐点以及延迟的变化情况 。 

```bash
# 渐进式压测，从32线程开始，逐步增加
for threads in 32 64 128 256 512; do
    echo "Testing with $threads threads..."
    /home/yashan/sysbench/src/sysbench /home/yashan/sysbench/src/lua/oltp_read_write.lua \
        --report-interval=5 \
        --tables=10 \
        --table_size=100000 \
        --yashan-db="192.168.1.2:1688" \
        --yashan-user="sysbench" \
        --yashan-password="$YASHAN_PASSWORD" \
        --time=300 \
        --threads=$threads \
        --thread-init-timeout=1000 \
        run \
        --percentile=99
done
```

#### 表数量和表大小调优

根据测试目标选择合适的表数量和表大小：

```bash
# 减少表数量，增加每个表的行数，适合测试大表性能
--tables=5
--table_size=200000

# 增加表数量，减少每个表的行数，适合测试高并发小表访问
--tables=20
--table_size=50000
```

#### 测试场景选择

根据测试目标选择合适的测试场景：

| 场景 | 考察重点 |
| --- | --- |
| 点查询（point_select） | 主键单行查询性能 |
| 只读（read_only） | 复杂只读查询和索引扫描能力 |
| 只写（write_only） | 纯写入（INSERT/UPDATE/DELETE）性能 |
| 读写混合（read_write） | 综合OLTP事务处理能力 |
| 索引更新（index_update） | 索引列的更新性能 |
| 非索引更新（non_index_update） | 非索引列的更新性能 |

### 调优过程指标关注

在调优过程中，应关注以下关键指标的变化：

- **TPS (transactions per second)**：每秒事务数，是衡量系统吞吐量的核心指标

- **QPS (queries per second)**：每秒查询数，反映数据库处理查询的能力

- **latency**：事务响应时间，包括平均响应时间和分位数响应时间

- **threads fairness**：线程公平性指标，stddev越小表示各线程负载越均衡

通过分析上述指标的变化，可以判断当前配置是否达到最佳性能，并指导进一步的调优方向。

## 性能问题定位

根据监控数据进行性能问题定位：

| 现象 | 可能原因 | 解决方法 |
| ---------------- | -------------------- | ---------------- |
| TPS低，CPU利用率高 | SQL执行效率低，存在全表扫描 | 添加索引，优化SQL |
| TPS低，IO利用率高 | 磁盘IO瓶颈 | 使用更高性能的SSD，优化数据布局 |
| TPS低，内存使用率高 | 内存不足，频繁换页 | 增加内存，调大缓冲区 |
| 延迟高，响应时间长 | 锁竞争或等待事件 | 分析等待事件，优化并发控制 |
| 线程负载不均衡 | 数据库进程未绑核或CPU调度问题 | 绑定数据库进程到特定NUMA节点 |
