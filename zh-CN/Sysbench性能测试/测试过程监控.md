在进行Sysbench性能测试时，监控数据库和操作系统的运行状态可以帮助分析性能瓶颈点，指导进一步的调优方向。本章节将介绍Sysbench测试过程中需要关注的监控指标和监控方法。

## 操作系统监控

### CPU监控

使用top或mpstat命令监控CPU使用情况：

```bash
# 实时查看CPU使用情况
$ top -bn1 | head -20

# 按CPU核心查看使用情况
$ mpstat -P ALL 1

# 查看各CPU核心的负载
$ sar -P ALL 1
```

关键监控指标：

- **%usr**：用户空间CPU使用率

- **%sys**：内核空间CPU使用率

- **%iowait**：等待IO的CPU时间比例，高值表示存在IO瓶颈

- **%idle**：空闲CPU比例

### 内存监控

```bash
# 查看内存使用情况
$ free -h

# 实时监控内存变化
$ vmstat 1

# 查看内存详细信息
$ cat /proc/meminfo
```

关键监控指标：

- **used**：已使用内存

- **free**：空闲内存

- **buff/cache**：缓冲区/缓存内存

- **available**：可用内存

- **si/so**：Swap入/出内存，高值表示内存不足

### IO监控

```bash
# 查看IO使用情况
$ iostat -x 1

# 查看IO设备详细信息
$ iostat -dx 1

# 监控IO请求队列长度
$ sar -d 1
```

关键监控指标：

- **%util**：IO设备利用率，高值表示IO存在瓶颈

- **r/s, w/s**：每秒读写请求数

- **rMB/s, wMB/s**：每秒读写字节数

- **await**：IO请求平均等待时间

- **svctm**：IO请求平均服务时间

### 磁盘性能测试

使用fio测试工具：

| 测试场景 | 说明 |
| --- | --- |
| redo盘 | 同步写，顺序写，blocksize=512 |
| 数据盘 | 同步写，随机写/读，blocksize=8k |
| 集群场景 | 使用direct io |

```bash
#!/bin/bash
DEVICE=/home/wangshaohua/fio_test
RUNTIME=30

echo "=== 同步 I/O 顺序写 ==="
sudo fio --name=sync_seq --filename=$DEVICE --direct=0 --rw=write \
  --bs=4k --numjobs=1 --iodepth=1 --runtime=$RUNTIME --time_based \
  --group_reporting --ioengine=sync --size=1G

echo "=== 同步 I/O 随机写 ==="
sudo fio --name=sync_rand --filename=$DEVICE --direct=0 --rw=randwrite \
  --bs=4k --numjobs=16 --iodepth=1 --runtime=$RUNTIME --time_based \
  --group_reporting --ioengine=sync --size=1G
```

## 数据库监控

### 读场景分析

- 关注是否能够缓存全部的数据

  ```sql
  -- 1. 查看DATA_BUFFER_SIZE参数
  show parameter data_buffer_size

  -- 2. 查看sysbench所对应用户的数据文件大小
  SELECT SUM(BYTES) AS TOTAL_USER_SPACE FROM DBA_SEGMENTS WHERE OWNER = upper('username');

  -- 3. 查看DATA_BUFFER_SIZE总体统计
  SELECT * FROM V$BUFFER_POOL_STATISTICS;
  ```

- 关注磁盘随机读性能

  ```bash
  # 1. 确认是否达到磁盘带宽rMB/s上限、磁盘利用率%util是否到100%、IO延迟情况以及r_wait时间
  $ iostat -xm 1
  
  # 2. 查看数据库各个线程的IO使用情况，可以和单线程下IO进行对比，确认是否存在线程IO被抢占导致性能下降
  $ sudo iotop
  ```

### 写场景分析

- 关注redo是否分盘部署

  在写入场景中，会产生大量的redo日志（大约每个事务生成8K，此数据仅供参考，实际需结合时间观察来判断）。通过对redo进行分盘配置，充分利用磁盘性能，能显著提升实际测试效果。redo操作属于顺序写，是纯粹的写I/O；而数据操作涉及读写，属于随机读写。可综合两者特点，来决定将redo置于哪个磁盘。

- 关注redo block size大小是否合适

  推荐值为512，可依据测试结果酌情调整。在磁盘IO成为瓶颈的情况下，该值会产生一定程度的影响。 


- 关注DBWR_COUNT配置

  DBWR_COUNT是指实际执行刷脏页操作的线程数量。合理配置该参数，能够充分发挥磁盘IO性能，及时完成脏页刷新工作。然而，脏页并非刷得越快就越好，过快刷脏页会抢占写入场景下的IO资源。另外，若dbwr线程大部分时间都在执行checkpoint操作就无法及时对数据缓存（Data Buffer）中的buffer进行清理，这可能致使大量读IO同时发生，进而使得读IO在写入场景中成为性能瓶颈。

  从稳定性角度推荐的配置如下：

  - 稳定性优先：DBWR_COUNT = 1

  - 追求极限性能（但可能性能波动较大，在高并发场景下易因读IO抢占而导致性能下降）：DBWR_COUNT = 8

- 关注checkpoint策略是否合适

  如果没有高可用切换等故障恢复需求，建议配置如下：

  | 相关参数| 配置建议| 配置说明|
  | ----------- | -------- | -------- |
  | CHECKPOINT_INTERVAL | redo文件总大小的一半 | 将IO资源让渡给buffer清理操作，优先释放出更大的缓存空间。 |
  | CHECKPOINT_TIMEOUT |  120  | 确保及时更新checkpoint，防止出现redo追尾的情况。 |

### 等待事件监控

在YashanDB中，V$SYSTEM_EVENT/GV$SYSTEM_EVENT视图显示了系统当前的等待事件信息。通过分析等待事件可以定位数据库性能瓶颈。

查询当前等待事件：

```sql
-- 查看当前系统等待事件
SELECT event, wait_time, wait_count FROM V$SYSTEM_EVENT ORDER BY wait_time DESC;

-- 查看全局等待事件
SELECT inst_id, event, wait_time, wait_count FROM GV$SYSTEM_EVENT ORDER BY wait_time DESC;
```

常见等待事件及其处理方法如下：

| 等待事件 | 可能原因 | 处理办法 |
| --- | --- | --- |
| extending data file | 触发了表空间自动扩展 | 根据实际需要，提前预制好数据文件大小 |
| undo segment extending | 触发了undo文件自动扩展 | alter database datafile 'undo' resize 10G; |
| swap extending data file | 触发了swap文件自动扩展 | ALTER DATABASE TEMPFILE 'swap' RESIZE 6G; |
| xslot busy wait | 建表时设置的initrans太小，事务在block上无可用xslot，需申请等待 | 实际验证initrans=2性能比initrans=128要好 |
| log file parallel write | redo刷盘等待 | 改小redo的BLOCKSIZE，多为io瓶颈，可把redo与数据文件分盘 |
| log file sync | 事务提交时等待LGWR进程将REDO日志写入磁盘 | 调大REDO_BUFFER_SIZE，增加REDO_BUFFER_PARTS分区数 |
| db file scattered read | 数据块物理读等待事件 | 确认磁盘IO性能，优化SQL语句增加索引 |
| db file sequential read | 数据块顺序读等待事件，通常发生在索引扫描时 | 增加数据缓冲区大小，优化索引 |
| free buffer wait | 数据缓冲区不足，等待空闲缓冲区 | 调大数据缓冲区DATA_BUFFER_SIZE，增加DBWR_COUNT |
| buffer busy wait | 热点块访问等待 | 调整PCTFREE参数，使用分区表 |
| redo追尾 | redo的status都是active和current | 增加redo数 |
| redo remote send | redo发送等待 | 调大_REPLICATION_BUFFER_SIZE参数值 |
| redo remote sync complete | redo等待备库同步等待 | 调大RECOVERY_PARALLELISM参数值 |

重复测试时，推荐手动执行checkpoint并切换redo：

```sql
-- 使内存中的脏数据写入到磁盘中
ALTER SYSTEM CHECKPOINT;

-- 对当前正在写入的redo日志进行归档，同时切换至下一可用redo日志文件
ALTER SYSTEM ARCHIVE LOG CURRENT; 

-- 强制切换当前正在写入的redo日志
ALTER SYSTEM SWITCH LOGFILE; 
```

### 缓存命中率监控

```sql
-- 查看数据缓冲区命中率
SELECT name, value FROM V$SYSSTAT WHERE name LIKE '%buffer%';

-- 查看具体命中率计算
SELECT
    CASE WHEN (a.value + b.value) = 0 THEN 0
    ELSE ROUND(a.value / (a.value + b.value) * 100, 2)
    END AS hit_rate
FROM
    (SELECT value FROM V$SYSSTAT WHERE name = 'consistent gets') a,
    (SELECT value FROM V$SYSSTAT WHERE name = 'physical reads') b;
```

关键指标：

- **consistent gets**：一致性读取次数

- **physical reads**：物理读取次数

- **buffer hit rate**：缓冲区命中率，应保持在95%以上

## Sysbench自带统计

Sysbench在测试过程中会实时输出统计信息，可以通过--report-interval参数控制输出间隔：

```bash
# 每10秒输出一次统计信息
/home/yashan/sysbench/src/sysbench /home/yashan/sysbench/src/lua/oltp_read_write.lua \
    --report-interval=5 \
    --tables=10 \
    --table_size=100000 \
    --yashan-db="192.168.1.2:1688" \
    --yashan-user="sysbench" \
    --yashan-password="$YASHAN_PASSWORD" \
    --time=600 \
    --threads=256 \
    --thread-init-timeout=1000 \
    run \
    --percentile=99
```

关键输出指标：

- **transactions**：已执行的事务总数

- **transactions/sec**：每秒事务数（TPS）

- **queries**：已执行的查询总数

- **queries/sec**：每秒查询数（QPS）

- **avg latency**：平均响应时间

- **95th/99th percentile**：分位数响应时间

## 常见问题与处理

### 1. 唯一索引冲突

- **问题**：唯一索引冲突导致测试失败

- **处理方案**：调整配置参数`_CONSISTENT_WRITE`，修改row movement。

### 2. 大并发下Sysbench启动超时

- **问题**：高并发场景下Sysbench启动超时

- **处理方案**：考虑设置timeout参数。

### 3. 大并发下性能下降

- **问题**：Sysbench大并发下性能下降

- **处理方案**：检查`max_reactor_channels`、`max_workers`参数配置，通过这两个参数限制数据库的实际并发数量。

### 4. 只读场景（write_only）下读特别高

- **问题**：只读场景（write_only）下读特别高

- **问题分析**：这种情况可能具有一定合理性。经计算，在随机场景下，读操作的IO量可能达到写操作的20倍。
